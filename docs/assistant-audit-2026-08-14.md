## 3. Дыры

### Корневая

**Д13. Слой инструментов не умеет говорить «нет».** 67 из 93 инструментов возвращают
отказ текстом внутри успешного ответа и никогда не выставляют `isError`. В телеметрии
у каждого провала стоит `"isError": false`, причина спрятана прозой на третьем уровне

- **Д1.** `create_dimensions` рапортует `Success: true` при `created 0`. Пять вызовов дали

## 5. Обратная связь: как довести до рабочего состояния

Не один баг, а незамкнутый контур: архитектор жалуется — жалоба никуда не доходит.
Четыре стадии, каждая нужна.

### Стадия 1 — собрать (Д20, Д19)

1. **Живой путь пишет запись хода.** В `CursorBridgeAgentHost` по завершении хода заполнить
   `TurnLogEntry` тем, что у него уже есть: текст запроса, документ, вид, модель из `done`,
   цепочку из `doneSummary`, число раундов, миллисекунды, исход. Без этого остальные три
   стадии бессмысленны.
2. **Кнопку — в честное состояние.** Триггер на `IsEnabled=false` (серая заливка, обычный
   курсор), тег сделать необязательным: одного комментария достаточно.
3. **Снять глушитель.** `WriteRatingPatch` обёрнут в `catch { }` без следа — если запись не
   прошла, архитектор уверен, что пожаловался. Хотя бы `Trace.WriteLine` и галочка
   «отправлено» в интерфейсе.
4. **Скриншот вида по кнопке.** Половина дефектов видна только глазами (цвет, лишние линии,
   положение). `ExportImage` активного вида к жалобе дешевле, чем просить архитектора
   делать это вручную.

### Стадия 2 — сохранить так, чтобы не потерялось

1. **Сшивать по `turnId` четыре источника** (см. раздел 1): `command-metrics` даёт успех и
   длительность команды Revit, `run_events.ndjson` — аргументы и ответы вызовов,
   `assistant-bridge.log` — границы хода, `assistant-sessions` — оценку.
2. **Убрать одноразовость экспорта.** Сейчас `📊` помечает жалобы выгруженными через
   `feedback-exported-ids.txt`, второй раз они в отчёт не попадут. Экспорт должен быть
   повторяемым, «только новые» — отдельным флажком.
3. **Общее место вместо машины архитектора.** Сейчас всё в `Logs\` на конкретном компьютере.
   Минимум — папка на сетевом диске с машиной и датой в имени. Дальше — отправка в Linear или
   GitHub Issues по webhook прямо из панели.

### Стадия 3 — увидеть

1. **Сводка вместо чтения .md подряд**: группировка по тегу и по инструменту в цепочке. Какой
   инструмент чаще всех присутствует в жалобах — то и чинить первым. Очередь работ, основанная
   на боли архитекторов, а не на догадках.
2. Счётчик `📊 N` в панели уже есть — после стадии 1 начнёт показывать осмысленное число.

### Стадия 4 — устранить и замкнуть круг

1. **Жалоба → тикет.** `.cursor/rules/assistant-feedback-triage.mdc` уже описывает разбор жалоб
   в тикеты и ждёт файл `assistant-feedback_*.md`. Заработает сразу после стадии 1 — сейчас ему
   нечего разбирать.
2. **Тикет → золотая фраза.** Каждая подтверждённая жалоба идёт в набор приёмки из P3. Тогда
   однажды исправленное не ломается заново — именно этого сейчас нет, поэтому нарушения
   «мы вроде уже исправляли» всплывают повторно.

## 6. Порядок работ

| Этап | Что | Дыры |
|---|---|---|
| **P−1** | Починить обратную связь | Д20, Д19 |
| **P0** | Инструменты перестают врать | Д13, Д1–Д4, Д14, Д18 |
| **P1** | Меньше ходов на ту же работу | Д5–Д8 |
| **P2** | Контекст и выбор модели | Д9–Д11 |
| **P3** | Тесты на живом пути + золотой набор | Д12, Д15, Д16 |

**P−1 идёт вперёд P0** не потому, что важнее, а потому что самый дешёвый (полдня) и
единственный, после которого виден результат всех следующих. Пока журнал ходов не пишется,
тестирование идёт вхолостую.

### Что делать в P0

1. **Общая обёртка результата (Д13)** вместо 93 самописных: неудача — это `isError: true`
   плюс машинно-читаемое тело `{ ok, created, failed, reason, hint }`. Пока этого нет,
   остальное чинит симптомы.
2. **Дать геометрии голос (Д14)** — в `DimensionAnnotationHelper` возвращать причину отказа
   вместо `null`.
3. **Запрет на ложный успех (Д1, Д18)** — `Success = false`, если создано 0 из N; отчёт по
   каждой записи; ошибка одной записи не выбрасывает весь цикл.
4. **`.strict()` на схемах (Д2)** — неизвестный аргумент это явная ошибка со списком
   принимаемых имён, плюс мягкий алиас `category` → `categoryList`.
5. **Словарь русских имён параметров (Д3)** — двусторонний, с подсказкой из 5 ближайших
   существующих имён при промахе.
6. **`tag_elements` (Д4)** — настоящая марка Revit по категории и списку id.

### Что делать в P1–P3

- **P1:** убрать красный из дефолта выносок; `set_elements_parameters` пакетом; честная
  пагинация (`TotalCount`/`HasMore`); развести инструменты-двойники.
- **P2:** профиль `annotation` вместо ключевых слов; 12–18 инструментов на профиль;
  `REVIT_SYSTEM_PREFIX` перенести в инструкции агента (один раз, не в каждое сообщение);
  `alwaysApply: false` для `revit-mcp.mdc`; закрепить `claude-sonnet-5` на авторской работе
  вместо авто-роутера.
- **P3:** перевести тесты на живой путь; метрики хода в лог; золотой набор из 10–15 фраз с
  порогами (вызовов ≤ 10, впустую 0, ложных успехов 0, ≤ 60 с), обязательно покрыв ветки,
  которых нет в логе.
