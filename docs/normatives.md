# Нормативы: откуда берутся правила и почему у всех одинаково

Как PDF из `normatives/` превращается в правила, которые применяют проверки —
и что нужно сделать, чтобы у каждого, кто клонировал репозиторий, нормы
работали так же. Windows и macOS одинаково.

## Кто что читает

```
normatives/*.pdf  ──seed──►  server/revit-data.db  ──export──►  plugin/Resources/norm-catalog.json
   (в гите)                   (локальная, в гит НЕ идёт)              (в гите)
                                      │                                    │
                                      ▼                                    ▼
                          проверки MCP (check_*, run_norm_audit)   ассистент внутри Revit
```

| Источник | В гите | Кто читает |
|---|---|---|
| `normatives/*.pdf` | да | пересев |
| `server/revit-data.db` | **нет** | MCP-инструменты: `check_*`, `run_norm_audit`, `query_norm_rules` |
| `plugin/Resources/norm-catalog.json` | **да** | ассистент в панели Revit (`NormCatalogStore.cs`) |

Каталог для ассистента лежит в гите — поэтому панель у всех одинаковая сразу
после `git pull`. База MCP собирается локально из тех же PDF, поэтому её надо
один раз собрать у себя.

## После клонирования репозитория

```bash
cd server
npm install
npm run seed:norms -- --prune
```

Займёт около минуты. Должно получиться **1508 правил из 19 файлов**. Проверить:

```bash
npm run norms:verify
```

Ожидаемый ответ — «Каталог совпадает с нормативами — у всех будет одинаково».
Эта же проверка идёт в CI на каждый push.

## Почему `--prune`

Без него пересев только добавляет. Правила, извлечённые прошлой версией
разборщика, остаются навсегда — и через несколько месяцев у двоих
разработчиков из одного репозитория оказываются разные библиотеки, а одна и та
же проверка отвечает по-разному. Так и было: локальная база доросла до 1715
правил там, где чистый пересев даёт 1508.

`--prune` удаляет всё, чего этот прогон не породил, и библиотека становится
функцией от PDF, а не суммой всех пересевов на этой машине.

**Осторожно:** правило, сохранённое архитектором через `save_norm_rule`, в этой
схеме неотличимо от засеянного, и `--prune` его тоже удалит. Поэтому флаг
выключен по умолчанию — включать осознанно, когда база считается собираемым
артефактом.

## Если поменяли PDF или разборщик

1. `npm run seed:norms -- --prune` — пересобрать библиотеку и каталог.
2. Закоммитить `plugin/Resources/norm-catalog.json` — иначе у панели в Revit
   останутся вчерашние нормы, а у проверок MCP будут сегодняшние, и никто об
   этом не узнает.
3. `npm run norms:verify` — убедиться, что сходится. CI проверит то же самое.

В диффе каталога всегда будет меняться строка `exportedAt` — это метка времени
сборки, не содержание.

## Что нормы знают, а чего нет

```bash
npm run norms:coverage            # таблица по документам
npm run norms:coverage -- --misses  # какие требования не разобрались
```

Покрытие считается не «правил на страницу» — страница определений законно не
даёт ничего, — а по пунктам, **сформулированным как требование** («должен», «не
менее», «не допускается»): сколько их и сколько попало в библиотеку.

Сейчас в среднем **67%** (1628 требований из 2441). Пять документов разобраны
на 98–100%, но четыре помечены **НЕ РАЗОБРАН**: у техрегламента по пожарной
безопасности на 145 страницах нашлось 5 требований — это не «низкое покрытие», а
документ, который не разобрался на пункты вообще. Чинить там надо текстовый слой
PDF, а не шаблоны разборщика.

Это важно понимать при чтении ответов: **по документу с нулевым покрытием
«нарушений не найдено» означает «мне нечем было проверить»**, а не
«соответствует».
