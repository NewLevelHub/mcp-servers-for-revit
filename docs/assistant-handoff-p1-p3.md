## 2. Что осталось — предмет работы

Порядок из аудита. P1 даёт архитектору наибольший видимый эффект, P2 — скорость,
P3 — защиту от регрессов.

### P1 — меньше ходов на ту же работу

- **Д5. Красный зашит в дефолт выносок.** `textTypeName` по умолчанию

  → `server/src/tools/set_element_parameter.ts`, `commandset/Services/SetElementParameterEventHandler.cs`
- **Д7. `TotalCount` / `HasMore` приходят null** — модель теряется в пагинации.
  Поля в модели уже есть (`commandset/Models/Common/AIResult.cs`), но обработчики их
  не заполняют.
- **Д8. Инструменты-двойники.** `create_text_note` / `create_text_notes`,
  `tag_all_walls` / `tag_walls`, три способа поставить размер. Разводить осторожно:

### P2 — контекст и выбор модели

Всё в `assistant-bridge/src/agent-session.ts`. **Осторожно: в этом файле лежат
незакоммиченные правки REV-157 — не откатывать.**

- **Д9. `HEAVY_TASK_HINTS`** — «размер», «марк» и т.п. тянут полный каталог (188 КБ),

- Аудит также предлагает закрепить `claude-sonnet-5` на авторской работе вместо

## 3. Что переиспользовать, а не изобретать заново

Это главное, ради чего написан документ.

**`server/src/utils/toolOutcome.ts` — общая обёртка результата.**
Подключена в `register.ts` через прокси `captureTools`, который оборачивает
последний аргумент-функцию каждого `server.tool(...)`. Следствия:

- Новым инструментам **не нужен свой `try/catch`** — брошенная ошибка сама станет
  `isError`. Смотрите `tag_elements.ts` как образец нового стиля.
- Чтобы инструмент честно отказал, достаточно вернуть в теле `Success: false`
  (или `success` / `ok`) с текстом в `Message` / `message` / `summary`.
- Обёртка намеренно **узкая**: только явный `false` на известном флаге. Проверка
  норм, нашедшая нарушение, успехом быть не перестаёт. Тесты на это —
  `toolOutcome.test.ts`, при правках их не ослаблять.

**`server/src/utils/revitCategories.ts`** — нормализация имён категорий
(`normalizeCategoryNames`). Использовать везде, где инструмент принимает категорию,
вместо новых самописных разборов.

**`commandset/Utils/ElementParameterHelper.cs`** — словарь имён параметров
(`ParameterAliasGroups`) и `DescribeMissingParameter` для подсказок. Для Д6
пакетную запись строить на этом же, не заводя второй словарь.

**Журнал ходов `TurnLogEntry`** (`plugin/Core/Assistant/AssistantTurnLog.cs`) уже
содержит `ToolCalls` с именем, аргументами, успехом и длительностью каждого вызова.
Для Д12 расширять его, а не строить параллельную телеметрию.
`FeedbackExporter.cs` уже умеет сшивать записи с оценками по `turnId` — для Д12/сводок
логика чтения там готова.

## 4. Ловушки этого репозитория

- **`LocalAgentHost.cs` — мёртвый код**, но удалять нельзя: на нём держатся тесты
  (Д15) и `LocalAgentHost.MaxHistoryChars` / `CollapseDoneSummary` / `ParseViewContext`
  используются живым путём. Живой путь — только `CursorBridgeAgentHost`.
- **Конфликт имён `ElementIdExtensions`.** В `commandset` подключён
  `Nice3point.Revit.Extensions` со своим одноимённым классом. Писать полное имя
  `RevitMCPCommandSet.Utils.ElementIdExtensions.FromLong(...)`, иначе `CS0104`.
  Для `.GetIntValue()` / `.GetValue()` достаточно `using RevitMCPCommandSet.Utils;`.
- **Никаких `TaskDialog.Show` в обработчиках.** Они выполняются внутри
  `ExternalEvent` во время хода агента — нажать некому, Revit встаёт. В файлах уже
  стоят комментарии-предупреждения; последний живой вызов убран (Д17).
- **Новый инструмент — это четыре места:** `server/src/tools/<имя>.ts`,
  `commandset/Services/...EventHandler.cs`, `commandset/Commands/...Command.cs`,
  запись в `command.json`. Проверять `node scripts/check-tool-registry.mjs`.
- **Сборка требует закрытого Revit** — иначе последний шаг (копирование DLL в папку
  аддинов) падает с «файл занят», хотя компиляция прошла.

## 5. Состояние дерева и как проверять

**Всё незакоммичено**, ветка `main`. В дереве три слоя правок:

1. **REV-157** (не мои): `assistant-bridge/src/*`, убранные модальные диалоги в ряде
   обработчиков, профиль `lite`, `docs/tool-registry.md`. **Не откатывать.**
2. **P−1** — обратная связь (см. таблицу выше).
3. **P0** — честные инструменты (см. таблицу выше).

Команды проверки:

```bash
# сервер: типы и тесты
cd server && npx tsc --noEmit && npm test     # ожидается 351 из 351

# согласованность инструментов и команд
node scripts/check-tool-registry.mjs          # 94 инструмента, 75 команд

# C#: обе сборки (Revit должен быть закрыт)
cd commandset && dotnet build -c "Debug R23"
cd plugin && dotnet build RevitMCPPlugin.csproj -c "Debug R23"
```

**В Revit живьём ничего из P−1/P0 не проверялось.** Приёмка на стороне архитектора,
чек-лист проверок передан отдельно.

Логи для разбора (папка одна):
`%APPDATA%\Autodesk\Revit\Addins\2023\revit_mcp_plugin\Logs\`
— `assistant-sessions_*.jsonl` (журнал ходов, до P−1 был пустым),
`assistant-feedback_*.md` (жалобы), `command-metrics_*.jsonl` (что делал Revit).

## 6. Как работать дальше

- **Границы этапа соблюдать.** Брать P1 целиком либо по дырам, но не размазывать
  по всем трём этапам сразу — иначе непонятно, что дало эффект.
- **Аудит проверять, а не верить на слово.** Он писался по логам и чтению кода, без
  живого запуска, и в двух местах уже разошёлся с реальностью (раздел 1). Если код
  говорит другое — верить коду и сказать об этом прямо.
- **Дыры сверх аудита чинить**, если попались по дороге и они в границах этапа;
  обязательно называть их в отчёте отдельно от плановых.
- Аудит честно оговаривает свои границы: в логе фигурировало 15 инструментов из 94,
  по DWG, спецификациям, листам, лестницам и нормоконтролю данных нет вообще.
  Список дыр полон только в пределах разобранного сценария.
